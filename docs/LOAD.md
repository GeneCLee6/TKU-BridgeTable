# 負載測試（H3，`e11-t21`）

這份文件記錄淡江牌桌在「很多人、很多桌同時打」時撐不撐得住：怎麼測、量到什麼、哪裡先撐不住、下一步做什麼。指標與系統狀態頁（`e11-t22`）的設計在 `ARCHITECTURE.md` §5.13，維運步驟在 `DEPLOY.md` §4.7。

## 1. 工具

| 工具 | 跑在哪 | 量什麼 |
| --- | --- | --- |
| `npm run load`（`scripts/load/`） | Node，對本機 `vite dev`（workerd）、staging 或 PR 預覽；**拒絕正式站** | 端到端：每個模擬社員從送出動作到收到「生效了」的訊息的延遲（p50／p95／p99）、斷線與重連、錯誤、這次用掉多少額度 |
| `tests/worker/load-cpu.test.ts` | Node（Vitest），真的 `ClubService`＋每桌一個 `TableHost`，經 structured clone 模擬 RPC，虛擬時鐘 | 每個物件每次被叫醒（socket 訊息、alarm、RPC）**自己**花的 CPU，不含它呼叫別的物件的時間；社團與每一桌忙碌的比例 |

為什麼兩個：Workers 裡的時鐘只在 I/O 之後前進，本機的 workerd 量到的是牆鐘（含本機 SQLite 寫入與其他程式搶 CPU），都不是 CPU。CPU 要在 Node 裡量純邏輯（記憶體儲存），正式環境再看 Workers Logs 的 `$workers.cpuTimeMs`。

### 模擬的社員（`scripts/load/client.ts`、`player.ts`）

- 用 HTTP 登入、開 `/ws`，在桌上時再開 `/ws/table/<id>`（跟瀏覽器一樣，`ARCHITECTURE.md` §5.10），每 15 秒 `ping`。
- 只看伺服器給的 `legalCalls`／`legalCards` 決定叫什麼、出什麼（沒人叫過就常開叫，所以大部分牌會打完 52 張），每步平均想 2 秒（`--think`，0.5～1.5 倍隨機）。
- 每個動作計時到「看得出它生效」的那則訊息：叫牌出牌是桌上的進度往前、開桌入座是大廳的 `myTableId`、聊天是聊天室出現那句、私訊是 `direct`；收到 `error` 或 15 秒沒回應算失敗。
- 大廳裡的人每分鐘做一件事：翻紀錄頁、讀 `/api/me`、或私訊另一位；桌上每 20 秒有人說一句話。
- `--churn 0.02`：每 30 秒每人 2% 的機率斷線（兩條連線一起），1～3 秒後重連。
- `--challenge 3`：三個人開一場一副的挑戰（建立、接受、各自開挑戰桌打完），看它結算（驗證 `EventObject`，§4）。

帳號：網站的第一個帳號（`--admin`，空的網站會先註冊）用管理 API 建 `load001`…，密碼與邀請碼從 `LOAD_PASSWORD`、`LOAD_INVITE_CODE` 讀，不進 shell 歷史。本機要 200 人，`.dev.vars.preview` 設 `MAX_USERS=250`（`maxUsers` 的管理頁上限是 100）。

```bash
# 本機：.dev.vars.preview 放 INVITE_CODE=、MAX_USERS=250、EVENT_OBJECTS=on
CLOUDFLARE_ENV=preview npx vite --port 5199 --strictPort
LOAD_PASSWORD=loadtest1 npm run load -- --url http://localhost:5199 --users 200 --tables 30 --robot-tables 5 \
  --watchers 45 --minutes 10 --challenge 3 --churn 0.02 --out load.json
# CPU：
TBT_LOAD=full npx vitest run tests/worker/load-cpu.test.ts --project default --silent=false
```

## 2. 額度（同一個 Cloudflare 帳號，預覽、staging、正式站共用）

免費方案每天：Workers 請求 10 萬、Durable Object 請求 10 萬（WebSocket 收到的訊息 20 則算 1 個，RPC 與 alarm 每次算 1 個）、Durable Object 時間 13,000 GB-s（醒著的物件以 128 MB 計）。`scripts/load/budget.ts` 先依計畫估算，跑完再用實際的次數算一次；**對遠端的一次測試超過任何一項每日額度的 15% 就拒絕**（本機不限），一天合計不超過 30%。

估算的單位（每分鐘）：

| 來源 | 量 | 算到哪裡 |
| --- | --- | --- |
| 一位社員的 ping | 每條連線 4 則 | DO 請求 ÷20 |
| 四人桌 | 一副約 61 步×2 秒＋5 秒發牌 ≈ 2.1 分鐘；每步 1 則訊息 | DO 請求 ÷20 |
| 一人＋三個 TKB | 一副約 1.4 分鐘，約 39 步是機器人，每步一次 alarm | DO 請求 ×1 |
| 每副打完 | 發牌 alarm 1、桌→社團 RPC 約 3（目錄兩次、紀錄一次） | DO 請求 |
| 登入、開連線、翻頁 | 每次 1 | Workers＋DO 請求 |
| 醒著的物件 | 社團與有機器人的桌整段時間、只有人的桌約三分之一 | DO 時間 |

| 計畫 | Workers 請求 | DO 請求 | DO 時間 |
| --- | ---: | ---: | ---: |
| 本機完整：200 人、30 桌（5 桌 TKB）、45 人觀看、3 人挑戰、10 分鐘 | 1,177（1.2%） | 4,843（4.8%） | 1,117 GB-s（8.6%） |
| 遠端煙霧：30 人、5 桌（2 桌 TKB）、6 人觀看、3 人挑戰、5 分鐘 | 約 150（0.2%） | 約 600（0.6%） | 約 160 GB-s（1.2%） |

所以 200 人 30 桌在正式站打 **一小時** 約用 DO 時間的 50%、DO 請求的 30%：一個晚上的大型活動要先想好（§5）。

## 4. 本機完整負載：端到端（workerd）

`CLOUDFLARE_ENV=preview npx vite`（本機 workerd，`EVENT_OBJECTS=on`，跟 PR 預覽同一份設定），`npm run load` 200 人、30 桌（25 桌四人、5 桌一人＋三個 TKB）、45 人觀看、47 人在大廳、3 人挑戰、每 30 秒 2% 斷線重連，10 分鐘（含修正後的大廳廣播）。

| 動作 | 次數 | p50 ms | p95 ms | p99 ms | 最大 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 叫牌出牌（`call`＋`play`） | 7,992 | 12 | 442 | 1,296 | 7,505 |
| 聊天 | 29 | 15 | 861 | 1,039 | 1,039 |
| 私訊 | 139 | 75 | 1,277 | 1,619 | 1,765 |
| 紀錄頁（HTTP） | 139 | 27 | 619 | 1,827 | 2,673 |
| `/api/me` | 145 | 22 | 470 | 1,932 | 2,063 |
| 開桌 | 30 | 284 | 518 | 635 | 635 |
| 入座 | 75 | 493 | 815 | 1,069 | 1,069 |
| 觀看（45 人同時） | 45 | 2,064 | 2,350 | 2,355 | 2,355 |
| 離桌（結束時 135 人同時） | 135 | 2,516 | 7,968 | 9,193 | 10,011 |
| 登入（PBKDF2） | 200 | 793 | 892 | 1,137 | 1,137 |

- 10 分鐘打完 145 副、機器人 1,208 步（社團收到的回報），送出 8,467 則動作、14,996 個 ping，收到 15.7 萬則大廳與 4.4 萬則牌桌訊息。
- 失敗：2 個出牌 15 秒沒回應、16 個出牌剛好在斷線重連時送不出去（`unsent`），沒有伺服器錯誤（`crashes` 0、5xx 0）。
- 斷線重連 76 次全部接回來；`/api/health` 的重連率 26%（是 `--churn` 故意造成的），告警 `reconnectRate` 與 `actionSlow`（社團的動作 p95 落在 5 秒那一格，主要是結束時一起離桌）如預期亮起，系統狀態頁看得到。
- **讀法**：本機的 workerd 把所有 Durable Object 放在同一條執行緒，社團每次大廳廣播（約 0.2 秒）時桌子也得等，所以叫牌出牌的 p95／p99 被拉長；在 Cloudflare 上每個物件各自跑，桌子的延遲應該接近 p50。同時湧進社團的動作（45 人一起觀看、135 人一起離桌）要排隊，每個都要等一次廣播，這就是 §5 的瓶頸。
- 這次的用量（依實際次數估）：Workers 請求 1,186、DO 請求 4,578、DO 時間 1,153 GB-s，與事前估算（1,177／4,843／1,117）相符。

**`EventObject` 在 workerd 上第一次真的跑**（H2b 的接線之前只在 Node 測過）：挑戰建立後 `/api/health` 的 `events` 是 `{"objects":N,"unconfirmed":0}`（每場開著的挑戰一個物件，都收下了），三個人各自打完一副後挑戰在 115 秒內提前結束（`status: finished`、有名次），整段沒有 `crash`。另外先跑的 10 人小測試也一樣（61 秒結算）。

## 5. 瓶頸與建議

1. **大廳廣播（已經部分修正，還是第一個瓶頸）**。大廳任何一點變化（入座、發新一副、打完一副、私訊、有人上下線），社團就替每位在線的人算一份**完整的**大廳（全部社員、全部牌桌）再比對有沒有變。原本每份裡又各自掃一次所有牌桌與在線名單，所以是在線人數的平方以上：200 人時一次約 1 秒，30 桌每分鐘約 30 次變化，社團 109% 忙，排隊越來越長。這一批把每位觀看者共用的部分改成每次廣播算一次（`lobbyBasis`），降到約 0.2 秒、社團 28% 忙；但剩下的是**每人一份 35 KB 的 JSON**（200 人每次 7 MB，社團每分鐘送出 400 MB），在 Cloudflare 上也會吃掉社團的 CPU，免費方案每次呼叫的 CPU 上限下會被中止。**建議下一批（H4）**：大廳拆成「大家都一樣的」（社員名單與在線、牌桌列表）與「每個人的」（好友、封鎖、我在哪一桌、能不能進），共用的部分一次序列化、只在變的時候送，排序（好友置頂）交給瀏覽器；再進一步只送差異。做完之後社團每次變化應該是 O(在線人數) 的發送，而不是 O(在線人數²) 的計算。
2. **額度**：200 人 30 桌一小時約用掉 Durable Object 時間每日額度的 50%（有機器人的桌整段時間醒著）與 DO 請求的 30%，主要是 ping 與機器人的 alarm。辦一晚上的大活動要先估（`npm run load -- --dry-run` 可以只看估算），或在那之前升級 Workers 付費方案（每月 5 美元），由社長決定。
3. **牌桌**：每桌一個物件（H1）之後，一桌只有自己的四到八個人，出牌、機器人都在 2 ms 左右，最忙的一桌不到 1% 的時間；30 桌時桌子不是瓶頸。
4. **H2c（隊制賽搬到 `EventObject`）值不值得**：不急。量起來社團的時間幾乎都花在大廳廣播（修正前 10 分鐘裡社團花了約 655 秒，其中 653 秒是牌桌回報與私訊觸發的大廳廣播，其他所有呼叫加起來不到 1%）；隊制賽本來就沒有自己的期限工作、比分讀的時候才算，搬出去省不到社團的時間。建議先做 H4（大廳），H2c 等隊制賽真的同時很多場、或社團其他部分變成瓶頸再說。挑戰搬到 `EventObject`（H2b）在 workerd 上跑得起來（§4），正式站要不要開照 `DEPLOY.md` §4.6 由社長決定。
5. **Workers Logs**：每個動作一行日誌，200 人 30 桌一分鐘約 900 行，一小時約 5 萬行；免費方案一天 20 萬行，超過的會被取樣。大活動那天可以考慮把 `action` 改成取樣記錄。

## 6. 遠端煙霧測試

**還沒跑（2026-10-26）**：這個 PR（#142）的預覽沒有部署。`preview.yml` 要 `PREVIEW_INVITE_CODE` 這個 secret 才部署，repo 裡只有 `CLOUDFLARE_API_TOKEN` 與 `CLOUDFLARE_ACCOUNT_ID`（staging 同樣缺 `STAGING_INVITE_CODE`），所以每個 PR 的 Preview 都顯示「skipping the preview」。照規定不自己改 secret、不手動建 Worker，**遠端這次用掉的額度是 0**。

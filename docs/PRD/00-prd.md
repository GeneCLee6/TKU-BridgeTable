# PRD — TKU BridgeTable · 淡江牌桌

> 這是產品的總 PRD：願景、範圍、功能需求、驗收條件總表與里程碑。每個 epic 的細節、AC 勾選與 task 拆分在同一個資料夾的 `e*.md`，**勾選狀態以 epic 文件為準**。資料夾的閱讀方式與 task 格式見 [`README.md`](README.md)，BBO 的功能與機器人分析見 [`01-bbo-competitive-analysis.md`](01-bbo-competitive-analysis.md)。

## 1. 願景

**先做出淡江橋藝社自己的 BBO，再做成台灣（華語）橋牌社群的 BBO。**

- **M0（已上線）**：社員註冊、開桌、四人即時打牌、機器人補位、牌局紀錄，介面照 BBO。
- **M1 社團完整版**：社員提出的四大功能——聰明的 GIB（原本要可設等級；社長 2026-10-24 改成不分等級的 TKB，可學不同制度）、挑戰（單挑與多人排名）、雙桌隊制賽、牌局收藏／精選／篩選——加上它們需要的基礎。
- **M2 公開測試**：其他社團可以加入；機器人用模擬與雙明手分析；比賽、積分、練習與教學。
- **M3 商業化**：方案與金流、原生 App、用牌局資料訓練的機器人模型。

基本原則是 BBO 的核心功能都要有，並在 BBO 做得不夠好的地方超越它。

## 2. 背景與問題

淡江橋藝社社員平常在 BBO（Bridge Base Online）上一起打牌，但：

- 自己開桌、指定四個人一起打，需要 BBO premium 會員，每個人都要付費並不實際。
- 社員只需要「找自己人開一桌打牌、打完能回顧」，BBO 的很多功能用不到；反過來，社團需要的東西 BBO 沒有：
  - **GIB 只會一套 2/1 制度**，社團教的 5542 自然制與淡江特約，機器人搭檔配合不了。
  - **挑戰只能一對一**，社課想讓全社打同一組牌、排出名次做不到。
  - **牌局紀錄只能依帳號與日期查**，找「上次那副 4♠」「某人主打的牌」很難；也沒有幹部挑選、講解的精選牌局。
  - **隊制賽要湊齊 8 人、陽春的流程**，沒有準備室與即時比分。
- 打完的牌想拿來社課討論，需要一個大家都看得到的牌局紀錄。

## 3. 目標與非目標

**目標**

1. 社員註冊帳號後，可以開桌、找人坐下、四個人同時線上打完整的一副橋牌。（M0 ✅）
2. 叫牌與出牌的操作與畫面參照 BBO，社員不需要重新學習。（M0 ✅）
3. 規則由伺服器把關：不合法的叫品與出牌不會發生，看不到不該看的牌。（M0 ✅，新模式持續適用）
4. 每一副打完自動存成牌局紀錄，可重播、可在 BBO Handviewer 開啟；之後可收藏、精選與組合篩選。（M0 ✅ ／ M1）
5. 機器人照社團制度叫牌，能學不同制度，實力用評測數字證明。不分等級：現在是 TKB，伺服器有 DDS 之後加 TKB Adv（社長 2026-10-24）。（M1–M3）
6. 挑戰（單挑與多人排名）與雙桌隊制賽。（M1）
7. 比賽、積分、練習與教學。（M2）
8. 免費託管起步；成本隨規模成長時仍可負擔。（全程）

**現在的範圍（社長 2026-10-30）**：網站目前**只有淡江社團內部使用**。社團內部用得到的先做（ROADMAP「Phase V」）；只有開放給全台灣橋手才需要的功能（多社團、比賽積分、論壇、防作弊、多元登入等）收在 ROADMAP 的「全台灣橋手清單」，暫緩。多元登入（Email、Google、LINE）排在清單最後。

**非目標**

- 和 BBO 搶公開大廳的在線人數：先服務好社團（見 `01-bbo-competitive-analysis.md` §1）。
- 付費入場換獎金、虛擬幣（E12 AC-12.5）。
- 語音或視訊（社課用現有工具）。
- M0 的非目標（比賽、排名、IMP 比較、好友、私訊、計時）已移到後續里程碑。

## 5. 產品原則

1. **公平第一**：規則與可見性只在伺服器判斷；每個新模式都要回答「誰能看到什麼」。
2. **照 BBO，再超越**：熟悉的互動照抄；BBO 沒做好的地方才創新。
3. **機器人看得懂**：每個叫品都有意義與說明，制度可選。
4. **中文優先**：繁體中文、台灣用語；六種語言都要有。
5. **小步快跑**：一個 task 一個 PR、1–3 天可完成（[`README.md`](README.md#task-格式)）。
6. **數字說話**：機器人的實力、效能、規模都用可重現的測試與報告證明。

## 7. 使用者故事

**已上線（M0）**

1. 身為社員，我想用邀請碼註冊一個帳號，之後用帳號密碼登入。
2. 身為社員，我想開一張新桌，其他社員在大廳看到後點空位坐下。
3. 身為社員，四個人坐滿就自動發牌，不用再按任何按鈕。
4. 身為社員，我想像在 BBO 一樣用叫牌盒叫牌，按不了不合法的叫品。
5. 身為社員，我叫了特殊叫品時想 Alert 並寫說明，只有對手看得到。
6. 身為莊家，我想在首攻後看到並出夢家的牌。
7. 身為社員，手滑出錯時想請對手同意撤回。
8. 身為莊家，剩下的牌很明顯時想攤牌，由防守方接受；被拒絕時我的牌維持攤開，防家看得到四家的牌。
9. 身為社員，打完（或攤牌被接受）想看到合約、結果與分數，然後像 BBO 一樣自動發下一副，不用等四個人都按「下一副」。
10. 身為社員，我想在牌局紀錄裡回顧打過的每一副，逐墩重播（每墩四張自動依序出），或在 BBO Handviewer 開啟。
11. 身為社員，網路斷掉或重新整理之後，想回到原本的座位繼續打。
12. 身為社員，我想在手機上也能打。
13. 身為社員，人湊不齊時，我想放機器人補位，而且機器人叫的是我們社團的制度。
14. 身為社員，我想從語言選單切換繁中／簡中／英／越／日／韓，以及實體牌／文字牌。
15. 身為管理員，我想在網站上重設社員密碼、刪除帳號、調整人數上限與邀請碼。

## 9. 非功能需求

- **公平**：手牌只在伺服器；瀏覽器只收到它可以看的牌（`ARCHITECTURE.md` §4）。挑戰、隊制賽、雙人賽的資訊隔離由伺服器把關，並有集中的回歸測試（E11 AC-11.8）。
- **確定性**：同樣的牌、同樣的動作 → 同樣的機器人決定（E6），這是挑戰公平的基礎。
- **成本**：M1 維持 Cloudflare 免費方案（Workers＋SQLite Durable Object）；機器人運算環境另計（E6 AC-6.5）。
- **規模**：M0 為 10 個帳號、同時 2–3 桌；M1 為 50 個帳號、同時 5 桌；M2 為 200 個帳號、同時 30 桌（E11 AC-11.4）。
- **效能**：伺服器每個動作在 10 ms CPU 內；紀錄篩選第一頁 < 300 ms（E4 AC-4.8）；機器人思考上限 2 秒（E6 AC-6.5）。
- **無障礙**：牌、叫品、花色都有中文無障礙名稱；不只靠顏色表達狀態；M1 起可以只用鍵盤打完一副（E3 AC-3.9）。
- **隱私**：密碼以 PBKDF2 雜湊；訓練資料需同意且去識別化（E6 AC-6.11）；符合台灣個資法（E11 AC-11.10）。

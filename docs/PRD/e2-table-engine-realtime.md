## 背景

M0 的核心：`shared/` 的純函式橋牌引擎（發牌、叫牌、出牌、攤牌、撤回、計分），`ClubService` 在伺服器驗證每個動作，`worker/views.ts` 決定每個人看得到哪些牌，WebSocket 推送只送有變的部分（`00-prd.md` F2–F9、F11–F13）。這些都已上線並有測試。

下一步的挑戰（E7）、隊制賽（E8）、練習桌（E10）、雙人賽（E9）都是「同一套引擎、不同的牌桌規則」：牌從哪裡來（隨機／指定牌組／條件發牌）、打完做什麼（自動發下一副／記一副成績／停下來）、誰能看（觀看者、另一桌）。所以 E2 在 M1 最重要的一件事是**把牌桌做成可以掛不同模式**，而不是在 `service.ts` 裡到處加 `if`。

## 目標

- 一般牌桌的行為維持不變（所有現有測試保持通過）。
- 牌桌有 `mode`，每種模式透過掛勾決定發牌來源、結束後動作與紀錄寫法。
- 牌桌設定（公開／受邀、允許觀看）、計時、快速入座、斷線代打。
- M2：動作事件紀錄與裁判（TD）功能，給比賽用。

## 非目標

- 規則以外的畫面調整：歸 E3。
- 把 Durable Object 拆成每桌一個：歸 E11（AC-11.4），E2 只保證邏輯在 `ClubService` 內可以搬。
- 機器人怎麼決定：歸 E5、E6。

## 需求

### 功能

- `TableMode`：`casual`（現狀）、`challenge`（E7）、`team`（E8）、`practice`（E10）、`pairs`（E9）。
- `DealSource`：`random`（現狀，密碼學亂數）、`fixed`（指定的牌組，挑戰與隊制賽用）、`constrained`（條件發牌，練習用）。
- 牌桌設定：公開或只限受邀、是否允許觀看；房主可在牌桌上修改。
- 計時：每副時間上限（預設關）；輪到某人超過 60 秒有提醒；房主可請久未動作的人離座並由機器人接手。
- 斷線超過設定時間自動由機器人代打，本人回來後換回。

### 非功能

- **規則只在伺服器判斷**（`CLAUDE.md` 硬性規則 1）：新增的每個動作都在 `ClubService` 驗證並加 `tests/worker` 測試。
- **可見性只在 `worker/views.ts`**（硬性規則 2）：新模式的可見性改動要更新 `ARCHITECTURE.md` §4。
- 每個動作的伺服器處理時間在免費方案的 10 ms CPU 內（機器人思考除外，見 E6 AC-6.5）。

## 設計方向

- `Table` 加上 `mode` 與 `modeState`；`ClubService` 在「發新的一副」「一副結束」「寫紀錄」三個地方呼叫模式的掛勾（`TableModeHooks`）。`casual` 的掛勾就是現在的行為。
- `DealSource` 是純函式介面，放在 `shared/`；固定牌組的內容只存在伺服器，發到哪一副才放進 `BoardState.hands`。
- 計時用 Durable Object alarm；所有到期事件都經過同一個排程器（現有的機器人排程也併進來），避免多個 alarm 互相覆蓋。

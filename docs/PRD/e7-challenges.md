## 背景

產品需求第 2 點：要有 BBO 的挑戰功能。使用者可以單挑一位玩家，或挑戰多名玩家；被挑戰的人打同一組牌，打完之後比出結果，看誰第 1 到第 5 名（以及之後的名次）。功能要和 BBO 一樣，**使用者體驗與功能要比 BBO 好**。

BBO 的做法（[`01-bbo-competitive-analysis.md`](01-bbo-competitive-analysis.md) §5）：一對一、4–16 副、IMP／MP／總分、和 GIB 機器人一起打、Best Hand 與 Just Declare 選項、7 天內接受、建立後不能取消、雙方都打完才判勝負。官方沒有多人排名。

## 目標

- 單挑與多人（2–20 人）挑戰，所有參與者打同一組牌、坐同一方位，其他三家是用同一種制度的確定性機器人（TKB）。
- 完成者即時看到排名（第 1 到第 N 名），每副有 traveller，可以並排重播自己和任何一位對手。
- 比 BBO 好的體驗：沒人開打前可取消、一鍵再戰、「用這副牌挑戰」、每週社團挑戰、成績分享卡、挑戰大廳一眼看清進度與期限。
- 挑戰的牌局進入紀錄，可在 E4 篩選。

## 非目標

- 付費入場換取獎金（BBO 的 Challenge Reward）：不做，見 E12 AC-12.5。
- 多桌移位的雙人賽：歸 E9。這裡的「多人」是每個人各自和機器人打同一組牌。

## 需求

### 挑戰的設定

| 設定 | 選項 | 預設 |
| --- | --- | --- |
| 對象 | 一位（單挑）或多位（2–20 人）**好友**（被封鎖的不行）。選人是一個輸入框：點一下列出全部好友，打字即時篩選（輸入防抖），可多選 | — |
| 牌組 | **只用隨機牌**，選項只有 Best Hand 與 Just Declare；或從自己打過的牌「用這副牌挑戰」 | 隨機 |
| 副數 | 4–16 | 8 |
| 計分 | 單挑：IMP 或總分；多人：MP、Cross-IMP 或總分 | 單挑 IMP、多人 MP |
| 機器人 | TKB，用淡江制度或 2/1（GIB 相容）；**沒有等級**（社長 2026-10-24，E6） | 2/1 |
| Best Hand | 每副旋轉牌組，讓參與者拿四家中點力最高的一手 | 關 |
| Just Declare | 機器人叫牌，只選己方當莊的牌，參與者只打莊 | 關 |
| 截止時間 | 從發起那天算 1–7 天，所有人共用：回覆與打完都要在這之前 | 3 天 |
| 排名公開 | 只給參與者，或全社團 | 只給參與者 |

### 計分定義（`shared/challenge-scoring.ts`）

- **IMP（單挑）**：每副以兩人的南北分數差查 WBF IMP 表，累加。
- **總分**：每副南北分數加總。
- **MP（多人）**：每副，每贏過一位參與者得 2 分、平手 1 分；百分比＝得分 ÷（2 ×（人數 − 1））；總成績為各副平均。
- **Cross-IMP（多人）**：每副，和每一位其他參與者算 IMP，取平均；總成績為各副加總。
- **截止時間到了**：立刻停止，同 BBO，打到一半的那一副作廢、還沒打的不打了。**只有打完全部副數的人才排名，沒打完的人不排名、也不替他沒打的副算分（社長，2026-10-24）。** 10 人的挑戰只有 8 人打完，就只排那 8 人。（`challenge-scoring.ts` 的 Avg-／最差分保留給之後的比賽用，挑戰不用。）
  - 其他人在那一副只跟有打的人比，不跟沒打的人比。
  - 那一副只有一個人打時，他得 MP 50% 或 0 IMP。
  - 總分：沒打的副算那一副的最低分（沒人打就是 0）。
  - 以上三條 2026-10-24 社長確認（#38）。
- **同分**：同名次，下一名跳號（例如兩個第 2 名後是第 4 名）。

### 公平規則

- 所有參與者打同一組牌（同牌號、發牌者、身價），坐南；北東西是用同一種制度的 TKB。
- 機器人是確定性的（E6 AC-6.8：失誤的亂數種子＝牌局 id＋動作序號），所以兩個人只要做一樣的事，就會遇到一樣的機器人反應。
- 挑戰牌桌：沒有觀看者、不能撤回、不能換座位、每副只能打一次；攤牌由機器人用雙明手判斷（已有）。
- 打完之前看不到別人的結果與牌；挑戰的牌局在挑戰結束前，只有打完那一副的參與者看得到 traveller（E4 AC-4.9）。
- 「用這副牌挑戰」：發起者把自己打過（可先收藏）的牌拿來挑戰別人，他**不再打**，直接用他當時的結果計分、照樣排名，排名上標「已知牌」（2026-10-24 社長決定）。

## 設計方向

```
challenge（pending → active → finished｜cancelled｜expired）
  ├─ settings（上表）
  ├─ dealSet（N 副，伺服器產生；參與者開打那一副才揭露給他）
  ├─ players（invited → accepted｜declined；progress = 已完成副數）
  └─ results（player × board：合約、莊家、首攻、墩數、南北分數、牌局 id）
```

- 牌桌用 E2 的 `mode=challenge`、`DealSource=fixed`；一般牌桌行為不變。
- 期限用 E2 的統一排程器（Durable Object alarm）；結算是純函式，可在測試裡手算比對。
- M1 存在 `Club` Durable Object 的 SQL 表；E11 拆分後每個挑戰可以是一個 `Event` 物件。

## 風險與對策

- **機器人不確定導致不公平**：`e7-t09` 的確定性測試列為合併門檻；機器人運算環境（E6）逾時改用規則機器人時，要確保所有參與者都用同一種機器人（同一挑戰內鎖定機器人版本與等級）。
- **場外資訊**（先打完的人告訴還沒打的人）：無法完全防止；排名預設只給參與者看、牌局挑戰結束才公開，E11 AC-11.8 做異常報表。
- **單一 Durable Object 負擔**：M1 社團規模下沒問題；E11 拆分時挑戰獨立成 `Event` 物件。

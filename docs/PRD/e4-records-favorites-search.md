## 背景

M0 每副打完自動存成紀錄：`board:<id>` 存完整內容，`hist:`／`uhist:<userId>:` 存依時間排序的摘要索引，列表有頁碼與每頁筆數；詳細頁有 Handviewer 樣式的牌例、叫牌、逐墩重播、出牌紀錄、BBO Handviewer 連結與 LIN（`00-prd.md` F10、F19）。

社員的新需求（產品需求第 4 點）：

1. **收藏**：自己想留的牌局可以收藏，之後找得到。
2. **精選**：有些牌局值得全社看，要有人挑出來並寫講解。
3. **更多篩選與排序**：例如只看合約是 4♠ 的、只看某人主打的、只看某段日期的。

目前的 KV 索引只能「依時間往前翻」，做不到這些條件。Durable Object 的 SQLite 後端本來就支援 SQL（`ctx.storage.sql`），所以這個 epic 的關鍵是**加一份 SQL 摘要索引**，完整紀錄仍放在 KV。

## 目標

- 收藏（含私人筆記與標籤）與「我的收藏」。
- 精選（標題、分類、講解、逐墩講解）與「精選牌局」頁。
- 合約、莊家、參與者、搭檔、日期、結果、身價、牌桌、模式的組合篩選與排序，條件寫在網址可分享。
- 同一副牌的 traveller 與並排重播（M1，挑戰與隊制賽要用）。
- M2：雙明手分析（DD 表、par、每步損失）、PBN／整場 LIN 匯出、分享連結、匯入 BBO 的 LIN。

## 非目標

- 全文搜尋聊天內容。
- 跨社團的紀錄（E12 之後再說）。

## 需求

### 功能

- **合約篩選**：階數（1–7）＋花色（♣♦♥♠NT），可只選其一（例如「所有 4 線」「所有♠合約」）；可選「含 X／XX」或「只有 X／XX」；快捷鍵：成局、小滿貫、大滿貫、部分合約、四家 Pass。
- **莊家篩選**：莊家是誰（社員選單）、莊家方位（N／E／S／W），以及相對自己：我主打、同伴主打、敵方主打。
- **參與者篩選**：某位社員有打的、「我和 X 同桌」、「X 是我的搭檔」。
- **日期**：今天、本週、本月、自訂起訖。
- **其他**：結果（成約、倒約、超墩數）、身價、牌號、牌桌、模式（一般／挑戰／隊制賽／練習）。
- **排序**：日期（新→舊、舊→新）、南北分數、莊家墩數。
- **收藏**：每副可收藏／取消；收藏可加私人筆記與標籤；「我的收藏」可用標籤與上述篩選。
- **精選**：有 `boardCurate` 權限的人可把一副設為精選，填標題、分類（滿貫、防守、競叫、坐莊技巧、叫牌…）、講解（Markdown），以及「第 N 墩」的講解（重播到那一墩時顯示）。

### 非功能

- 一萬副紀錄時，任一篩選組合的第一頁在伺服器 < 300 ms。
- **資訊隔離**：挑戰與隊制賽進行中的牌局，在可以公開之前不出現在任何查詢結果（E7 AC-7.3、E8 AC-8.4）。查詢 API 一律套用這個過濾，不由前端決定。
- 查詢一律參數化 SQL；條件型別放在 `shared/`，前後端共用驗證。

## 設計方向

```
board:<id>              完整紀錄（不變）
SQL boards_index        每副一列：board_id, played_at, table_id, mode, event_id, board_no,
                        dealer, vul, level, strain, doubled, declarer_seat, declarer_user,
                        tricks, score_ns, claimed, reveal_at
SQL board_players       board_id, user_id, seat（四列，機器人 user_id 為 null）
SQL favorites           user_id, board_id, created_at, note, tags
SQL curations           board_id, title, category, body_md, trick_notes(json), curator, created_at
```

- 新紀錄寫 KV 的同時寫 SQL；舊紀錄用可續跑的回填一次搬完（`meta:schema` 升版）。
- `GET /api/history/search?level=4&strain=S&declarer=<userId>&from=2026-10-01&to=2026-10-31&sort=date_desc&page=1&size=20`，回傳摘要與總數。
- E11 若把紀錄搬到 D1（AC-11.4），這份 schema 原樣搬過去。

## 風險與對策

- **KV 與 SQL 兩份資料不一致**：同一個動作裡寫兩邊，失敗就整個動作失敗；回填可重跑；加一個「比對 KV 與 SQL 筆數」的管理指令。
- **資訊隔離漏網**：過濾放在查詢 API 唯一的入口（`e4-t15`），並列入 E11 的資訊隔離回歸測試（`e11-t13`）。
- **精選講解變成另一份橋譜**：講解只針對單副牌；制度與特約的說明連到淡江橋譜，不重寫。

## 背景

M0 已經有一套社團用的帳號系統：邀請碼＋管理員核准、PBKDF2 密碼、30 天 session、管理頁、忘記密碼，並與淡江橋譜共用帳號與權限（`00-prd.md` F1、F16、F17、F20、F21）。接下來挑戰（E7）、隊制賽（E8）都要「邀請某人」，需要好友、個人檔案與通知中心；公開測試（M2）之後還需要 Email 與第三方登入。

## 目標

- 社員可以設定個人檔案（含自評等級），其他人看得到。
- 好友、封鎖、私訊，讓「找人打牌」不用離開網站。
- 一個通知中心，承接挑戰邀請、隊制賽邀請、私訊等所有提醒（E7、E8、E9 共用）。
- 公開階段的身分驗證：Email、Google／LINE 登入、防大量註冊。

## 非目標

- 多社團（多租戶）帳號範圍：歸 E12。
- 大廳公開聊天室：社團規模不需要，M2 之後再評估。
- 付費會員與權益：歸 E12。

## 需求

### 功能

- 個人檔案：顯示名稱、自評等級（初學者／大專／公開組／橋士組，和機器人等級同一套名稱）、常用制度、自我介紹、頭像。
- 好友是單向「關注」，不需對方同意；封鎖會擋掉私訊、挑戰與隊制賽邀請，並隱藏對方的聊天。
- 通知中心：站內通知即時推送（WebSocket），離線時保留；M2 加 PWA 推播。
- 私訊：一對一、未讀數、分頁讀取、速率限制。

### 非功能

- 帳號相關的錯誤一律走 `ClubError`＋`shared/messages.ts` 代碼（六種語言）。
- 通知與私訊的資料量有上限（每人保留最近 500 則通知、每段對話最近 1,000 則），避免單一 Durable Object 變大。

## 設計方向

- 個人檔案放在 `StoredUser.profile`；好友 `friend:<userId>:<friendId>`、封鎖 `block:<userId>:<otherId>`；通知 `notif:<userId>:<時間>-<id>`；私訊 `dm:<對話id>:<時間>-<id>`，對話 id 由兩個 user id 排序後組成。
- 通知中心是一個小服務 `NotificationService`（在 `worker/`），由各 epic 的服務呼叫 `notify(userId, kind, payload)`；推送沿用現有的「只送有變的部分」機制。
- 等 E11 拆分 Durable Object 時，帳號、好友、通知留在 `Directory` 物件。

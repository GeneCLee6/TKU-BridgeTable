**做法建議**（2026-10-26 的分析，開工時照這裡，PR 裡寫明有沒有照）：

- **U0 橫向捲軸**：根因是 `HistoryRow.tsx` 的 `white-space: nowrap` 加上 `HistoryPage.tsx` 的 `overflow-x: auto`。改 `table-layout: fixed`、截斷、依寬度收欄，不要靠捲軸。
- **U0 換頁閃**：搜尋 API 一萬副只要十幾毫秒，閃的是前端：查詢一變就把列表換成骨架。問題全在前端，不要往伺服器找。
- **U0 文案**：「出過的牌反灰留著」改「已出牌淡化保留」（BBO 英文叫 Show played cards）。
- **U1 為什麼這樣分**：一百萬副首攻研究的標準誤只剩 0.001–0.01 墩，**再跑更多隨機副沒有用**；要的是 (1) 叫牌的新研究（首攻研究不涵蓋叫牌）、(2) 單明手抽樣校正雙明手偏差（DD 的首攻者等於看得到暗牌，攻 A、攻大牌被高估）、(3) 防守的 `compare` 大規模跑（還沒跑過）。每條改動都要過三關：該情境的模擬損失下降、`npm run eval` 對 main 不退步、題庫不退步。par 是雙明手、系統性偏向叫高，叫牌另用「跟替代叫品比」當第二個指標，兩個都差才是真弱點。
- **U1 之後**：這是一條持續的線（模擬 → 改規則 → 評測），不是做一次就完。真正「機器人自己在牌桌上模擬」是 Phase I，要先有伺服器 DDS（Phase P，付費）。

## 批次之間的原則

1. **同一 Phase 內依批次號做**；不同 Phase 之間只要前提滿足可以交錯（例如 D1 提案可以在 B 線進行時先出）。
2. 一批做不完（超過 3 天）就拆成兩個 PR，批次號加 a／b，不要把半成品合併。
3. 做到一半發現 PRD 的 task 定義有誤，**先在 PR 裡寫明採用的做法**，不要停下來等；真的要人決定的才停（例如 D1 的設計確認、未決問題）。
4. 每個 Phase 結束時跑一次完整回歸：`npm test`、300 副隨機牌、評測平台快速版（B7 之後）。

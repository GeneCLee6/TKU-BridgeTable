# eval/sim — 離線雙明手模擬：在社長的電腦上訓練 TKB

社團不付 Cloudflare 的錢（`ARCHITECTURE.md` §5.1.1），所以 TKB 在牌桌上只能照規則出牌。要讓規則變強，不用在伺服器跑 DDS：在社長自己的電腦上，用雙明手分析（DDS 的 WASM 版 `bridge-dds`，B11 已經是依賴）把幾萬到幾百萬副牌算完，看哪些規則對、哪些錯，再把結論寫回 `shared/robot/` 的規則。這裡是那套工具和第一個研究（首攻）。

只在 Node 跑（`npm run sim`），不進 Worker、不進瀏覽器的 bundle；跟 `eval/` 一樣用 Node 22 直接跑 TypeScript。結果放在 `eval/sim/data/`（不進 git，`.gitignore`），報告是 Markdown。

## 怎麼跑

```bash
npm run sim -- bench                                   # 量這台電腦的速度（單執行緒與多執行緒，約 1 分鐘）
npm run sim -- tables --deals 1000                     # 固定牌組前 1,000 副的 DD 表
npm run sim -- leads --deals 10000                     # 首攻研究：10,000 副（§4），約 1 分鐘
npm run sim -- leads --deals 1000000 --threads 18      # 過夜：1,000,000 副，約 2 小時（§5）
npm run sim -- leads --deals 2000 --samples 30         # 每副另外加首攻者自己的單明手抽樣估計（慢 30 倍）
npm run sim -- compare --deals 60 --samples 30         # TKB 對單明手抽樣：每一張牌（§3），約 2 分鐘
npm run sim -- compare --deals 500 --points lead       # 只比首攻
npm run sim -- compare --deals 5000 --points defence --threads 6   # 只比首攻之後的防守（§3.2），約 25 分鐘
npm run sim -- leads --deals 10000 --analyse           # 不算，只用檔案裡已有的紀錄重做報告
npm run sim -- replay --out data/leads-….jsonl         # 用這份程式的首攻規則重播一個首攻紀錄檔：舊首攻對新首攻（§8），不用再解 DDS
npm run sim -- leads --boards 清單.txt --samples 20 --out 檔  # 只算清單裡的副號（例如重播時首攻改變的副），加單明手抽樣
npm run sim -- bidding --deals 20000 --system gib --threads 8   # 叫牌研究：每個叫品對替代叫品（§7），約 40 分鐘
npm run sim -- compete --deals 10000 --system gib      # 同上，只看競叫的決策點
npm run sim -- bidding --deck slam --deals 5000 --system tku --threads 5   # 滿貫區的牌組（§9）
npm run sim -- bidding --deals 20000 --system gib --analyse --practice shared/practice-sets  # 重做報告並寫出練習牌組
```

| 參數 | 意思 |
| --- | --- |
| `--deals N`、`--from N` | 固定牌組（`eval/deals.ts`，種子 `tku-eval-v1`）第 `from` 副起 N 副；牌組不存檔，第 n 副由種子直接發，所以 1,000,000 副不用先準備 |
| `--seed s` | 換一組牌（跟 `npm run eval` 的 `--seed` 一樣） |
| `--deck slam` | 那個種子的滿貫區牌組（南北 30–36 點，或 26–29 點有 9 張配合；§9），`npm run eval` 也可以用 |
| `--system tku\|gib` | 四個 TKB 叫牌用哪套制度（預設 `tku`）；首攻與出牌的規則兩套一樣（`ROBOT.md` §3.2），差別只在叫牌過程與推論 |
| `--threads N` | 執行緒數，預設是邏輯處理器數 − 2（這台 i5-14500 是 18） |
| `--samples N` | `leads`：每副另外抽 N 個佈局做首攻者的單明手估計（預設 0）；`compare`：每個決策抽 N 個佈局（預設 30） |
| `--objective score\|tricks\|contract` | `compare` 比哪個：平均得分（預設，兼顧做成與超墩）、平均墩數、做成／倒合約的機率 |
| `--dd-bias t` | `compare`：雙明手偏差修正，每個佈局先把莊家扣 t 墩再判斷合約（§2） |
| `--points lead\|all\|defence` | `compare`：只比首攻、每一張牌（預設），或只比首攻之後防家的牌（§3.2） |
| `--out 檔`、`--report 檔` | 結果（JSON Lines）與報告（Markdown）的位置；預設在 `eval/sim/data/`，檔名含種子、制度與參數 |
| `--analyse` | 不算新的，只用檔案裡的紀錄重做報告 |
| `--boards 檔` | `leads`、`compare`、`replay`：只做檔案裡的副號（一行一個），取代 `--from`／`--deals` |
| `--changed 檔` | `replay`：把首攻改變的副號寫進這個檔（可以再給 `leads --boards` 做單明手抽樣） |

**中斷可以續跑**：結果一副一行寫進 JSON Lines，再跑同一個指令（同一個檔）會讀出已經算完的副號、只算剩下的。`Ctrl+C` 隨時可以停。`leads` 與 `compare` 的檔名最後有 TKB 規則的指紋（`-r` 加 8 碼，`shared/robot/` 所有檔案的雜湊）：規則沒變就接著同一個檔算，規則改了（例如下一個 PR 改了出牌）就自動開新檔，不會把新舊規則的結果混在一起；要接著舊的檔算或重做舊報告，用 `--out` 指定那個檔。

## 1. 多核心 DDS

WASM 版的 DDS 沒有執行緒，所以用 Node 的 `worker_threads`：每個執行緒載入自己的一份 DDS（`dds.ts`，約 0.1 秒、幾十 MB），主執行緒把**副號**分批送給空閒的執行緒（`pool.ts`、`worker.ts`、`jobs.ts`），執行緒自己從種子發牌、讓四個 TKB 叫完、解 DDS、把結果送回來；進度與 ETA 在 stderr。`bridge-dds` 只匯出 `CalcDDtablePBN`（整副 DD 表）、`SolveBoardPBN`（一個局面每張牌的墩數）、`DealerPar` 與 `AnalysePlayPBN`，沒有 `CalcAllTables`／`SolveAllBoards`，所以「批次」就是一個執行緒連續解很多副。`bridge-dds` 自己的包裝匯入沒寫副檔名，Node 讀不到，`dds.ts` 直接載 `dist/lib/dds.js` 的 emscripten 模組、照同樣的結構配置呼叫。

每個執行緒的 DDS 用 `SetMaxThreads(0)`；種子固定（抽樣的亂數種子是 `種子:副號:決策序號`），所以不管幾個執行緒、怎麼排程，同一副的結果一樣。

## 2. 單明手抽樣（`sampler.ts`、`score.ts`）

機器人在牌桌上看不到別人的牌（`CLAUDE.md` 硬性規則 6），所以「用 DDS 幫機器人想」要先抽出它看得到的資訊能容許的佈局：

1. **知道什麼**（`knowledgeOf`）：只用 `TableReading`（`shared/robot/reading.ts`，ROBOT.md §3.3）——自己的牌、首攻後的夢家（打夢家時加上莊家的牌）、已出的牌、沒跟出的花色、叫牌用機器人自己的制度讀出的各家張數與點力範圍。看不到的牌＝整副扣掉這些，從不讀 `state.hands` 裡別家的牌；測試把看不到的兩三家重新洗過，抽樣的問題與結果完全一樣。
2. **抽佈局**（`sampleLayouts`）：照 `shared/dealer.ts` 的方法拒絕抽樣——先依真實機率抽每家每門的張數（超幾何分布），不合張數範圍就丟掉，合了才發牌、再檢查點力；每個合條件的佈局機率一樣。一個佈局抽 5,000 次都不合（叫牌的推論跟牌矛盾，例如心理叫）就把條件各放寬一格（點力 ±1、張數 ±1）再抽，報告裡寫「放寬條件才抽到的比例」；**接受率**＝抽到的佈局數 ÷ 抽的次數。
3. **解與評分**（`score.ts`）：每個佈局用 DDS 解出每張合法牌之後我方拿幾墩；跨佈局算每張牌的**平均墩數**、**做成／倒合約的機率**（看自己是莊方還是防家）與**平均得分**（`duplicateScore`，有身價），三個都報，用哪個決定由 `--objective` 選。預設是平均得分：IMP 的場合合約最重要，但超墩也算一點。

**雙明手的偏差**：DDS 的莊家看得到四家的牌，飛牌一定飛對、不會被騙，所以雙明手高估莊家的墩數（文獻上真人莊家大約比雙明手少拿幾分之一墩，防家也一樣被高估）。`--dd-bias t` 是一個粗略的修正旋鈕：每個佈局先把莊家扣 t 墩（可以是小數，0.5 就是兩個整數結果各算一半）再判斷做成與得分；平均墩數不改。預設 0。合適的值要等 §3 的比較跟真人牌局對照後才知道。

## 3. TKB 對單明手抽樣（`compare.ts`）

```bash
npm run sim -- compare --deals 60 --samples 30            # 每一張牌，約 2 分鐘（14 執行緒）
```

一副牌由四個 TKB 叫完、打完；每個有選擇的出牌（合法牌超過一張）都用那一家的知識抽 N 個佈局、解 DDS、評分，拿 TKB 實際出的牌（`ruleBrain.play`，它只用自己的 `View`）跟抽樣最佳比；輸的決策連同損失（墩、做成率、得分）與情境記下來。所有牌結果一樣的決策（例如只差信號、或哪張都一樣）不算。情境：首攻（無王／王牌合約）、防家領出、防家第二／三／四家、防家墊牌或王吃、坐莊方領出／跟牌／墊牌或王吃。報告列每種情境的決策數、TKB 較差的比例與平均損失，以及損失最大的 25 個決策（副號、合約、座位、第幾墩、TKB 出的牌、最佳牌），給人看、也給之後改規則當目標。

| 防家領出 | 55.5 | 54.5 | 58.2 | 56.8 |
| 防家第二家 | 25.4 | 19.3 | 23.0 | 18.7 |
| 防家墊牌或王吃 | 17.3 | 17.6 | 16.9 | 17.8 |
| 防家第三家 | 16.0 | 10.0 | 17.6 | 10.0 |
| 防家第四家 | 8.0 | 5.2 | 6.7 | 5.4 |
| **合計** | **122.2** | **106.6** | **122.4** | **108.6** |

讀法與限制：

1. 這個數字是「每個決策對抽樣最佳的差」，不是整副的結果：改了一張牌之後的局面就不一樣，決策數也會變。所以每條規則最後還是看 `npm run eval` 的 IMP（`ROBOT.md` §3.9）；例如「無王先建立首攻的長門」在這裡幾乎看不出來，評測卻是最大的一條（+0.16 IMP／副）。
2. 接受率不到 1%：叫牌推論把佈局限制得很緊，強叫牌（例如 2NT 開叫、滿貫叫牌）之後放寬條件才抽到的比例較高，那些情境的結論要保守。
3. 單明手抽樣仍然是每個佈局雙明手解，莊家在每個佈局都猜對；`--dd-bias` 沒有用（0）。
4. 墊牌幾乎沒變：看過的大牌例多半是殘局（留哪一張大牌、王牌的自然墩要不要用來王吃），規則做不到。

## 4. 第一個研究：首攻（`leads.ts`）

**方法**：固定牌組每一副由四個 TKB 叫完（制度 `--system`），首攻者的手牌、叫牌過程與合約就是一個決策點；用實際牌局從首攻者的座位解 DDS，得到每一張首攻防家拿幾墩。幾萬副加起來就是 Bird–Anthias（*Winning Notrump Leads*）的做法：每副看不到的三家都是「合這段叫牌」的一個隨機佈局，所以對所有副取平均，就是對首攻者知道的事所容許的佈局取平均。`--samples N` 另外加首攻者自己在牌桌上能算的抽樣估計（§2）作對照，貴 N 倍。

**社長的觀念**各寫成一個情境加兩張候選牌（`CONCEPTS`）：A 是觀念說的首攻，B 是另一種選擇；兩張都用社團的慣例牌（`conventionalLead`，就是 TKB 用的 `shared/robot/lead-card.ts`：「01 第 4」，ROBOT.md §3；2026-10-26 以前是單張、雙張攻大、AK 攻 A、連張攻頂張、有大牌第四張、沒大牌三張攻大）。

| 觀念 | 情境 | A | B |
| --- | --- | --- | --- |
| 無王：同伴的花色 vs 自己的長門 | 無王合約，同伴叫過一門花色（首攻者依制度讀到 4 張以上）且自己有那門，自己另有 4 張以上的長門 | 同伴的花色 | 自己最長的花色 |
| 連張 vs 從大牌底下攻 | 一門 3 張以上的連張（AK、KQ、QJ、JT、T9 為首），另一門 3 張以上、有大牌但不連 | 連張頂張 | 從有大牌的那門攻小牌 |
| 攻王牌 | 王牌合約，王牌 2 張以上，另有 3 張以上的旁門 | 最小的王牌 | 最長旁門的慣例牌 |
| 短門 | 王牌合約，有王牌，一門非同伴的單張或沒大牌的雙張，另有 3 張以上的旁門 | 短門 | 最長旁門的慣例牌 |

每個觀念再分情境（同伴花色自己有幾張、無王／王牌、敵方有沒有叫過旁門、王牌有沒有大牌、有沒有王牌控制），報 A − B 的墩數（± 標準誤）、A 與 B 各自倒合約的比例、各自是最佳首攻的比例，以及 TKB 在這些情境攻了 A、B 或別的牌幾次、平均損失幾墩。報告另外列 TKB 各種首攻的損失，和 TKB 跟雙明手最佳首攻類型不同的情況（依總損失排序）。

讀法與結論：

1. **無王攻同伴的花色**：同伴的花色有 2 張以上就明顯比自己的長門好（+0.29、+0.50 墩，倒合約多 8–13 個百分點）；只有 1 張時差不多。TKB 已經這樣攻（規則「先攻同伴叫過的花色」），3 張以上時 28 副攻了別的牌，是「有大牌攻小、三張小牌攻大」之外的情況，可以看。
2. **連張 vs 從大牌底下攻**：連張頂張穩定多 0.25 墩、倒合約多 5 個百分點，無王和王牌合約都一樣。TKB 大多已經攻連張；無王有 195 副、王牌合約 636 副攻了別的（多半是 AK、單張、同伴的花色，排在連張前面），不一定錯。
3. **攻王牌**：每一種情境都是負的，尤其王牌有大牌時（−0.26）；敵方叫過旁門（夢家可能王吃）也沒有讓攻王牌變好。TKB 幾乎不攻王牌（42 副，平均損失 0.52 墩——它攻王牌時多半是沒別的可攻）。注意這是雙明手的偏見之一：莊家看得到牌，不會「因為被攻王牌而少吃一次」以外的失誤，被動首攻的價值被低估；要給攻王牌平反，得用 §3 的抽樣加 `--dd-bias` 看。
4. **短門**：單張在有沒有王牌控制下都好（+0.21、+0.18，最佳的比例 86% 對 68–70%）；**小雙張有王牌控制時也好（+0.14，最佳 82.7% 對 71.0%），TKB 卻只有 47／352 副攻雙張**。這是最清楚的規則缺口：王牌合約、有王牌 A 或 4 張以上王牌時，攻沒大牌的雙張。沒有王牌控制的小雙張差別小（+0.08）。

**TKB 損失最大的首攻**（跟雙明手最佳的類型不同，依總損失排）：無王從大牌底下攻小牌而最佳是「攻 A」（96 副，平均損失 1.69 墩）或「其他」（攻那門的大牌本身，111 副，1.42 墩）；王牌合約也是大牌底下的小牌 vs 攻 A（140 副，1.07 墩）。「攻 A」在雙明手下吃香是已知的偏見（它知道 A 不會被飛掉、也知道之後要攻什麼），真人攻 A 沒那麼好；但「大牌底下的小牌」在無王平均損失 0.51 墩、是最常見的首攻（1,093 副），值得用抽樣（§3）再看哪些該改攻別門。

## 5. 過夜大跑

```bash
npm run sim -- leads --deals 1000000 --threads 18          # 1,000,000 副首攻，約 2.5–3.5 小時
npm run sim -- leads --deals 1000000 --threads 18 --analyse  # 跑完（或中途）重做報告
npm run sim -- tables --deals 100000 --threads 18          # 100,000 副 DD 表，約 1–1.5 小時
npm run sim -- compare --deals 2000 --samples 50 --threads 18  # 2,000 副每張牌對照，約 2 小時
```

- 時間照上面的吞吐量估；中途 `Ctrl+C` 再跑同一個指令會接著算。要用全部 20 個執行緒就 `--threads 20`，電腦會變慢。
- **磁碟**：首攻紀錄一副約 300 bytes（10,000 副 3.0 MB，1,000,000 副約 300 MB），DD 表一副約 190 bytes（1,000,000 副約 190 MB）；`--samples` 的紀錄多兩個表，約兩倍；`compare` 一副幾 KB（只存輸掉的決策）。報告重做時逐行串流讀檔，1,000,000 筆也不用把整個檔放進記憶體。
- **記憶體**：每個執行緒一份 DDS，大約 100 MB 以內；18 個執行緒 2 GB 以內。
- 換制度（`--system gib`）或換種子是另一個檔，互不影響。

## 6. 下一步：把發現變成規則

1. 先把 §4 的結果拿給社長看：哪些觀念在雙明手下站得住（A − B 為正、A 倒合約比例較高），哪些要加條件（分情境後才成立）。
2. （首攻已做，§8）針對 TKB 損失最大的情況改 `shared/robot/play.ts` 的 `openingLead`（`ROBOT.md` §3 首攻那段同步改），每改一條用 `npm run sim -- leads --deals 100000 --analyse` 以外的新跑確認那一類的損失下降、整體不變差，再用 `npm run eval -- --set full` 對 main 確認 IMP 不退步。
3. `compare` 的其他情境（第二家、第三家、坐莊方）照同樣流程：先看損失最大的決策列表，找出規則漏掉的原則，再改。
4. 抽樣的接受率低的情境（強叫牌之後）可以改成先發大牌再補小牌的抽法；`--dd-bias` 的值要用真人的牌局（紀錄頁的 DD 表 vs 實際墩數）校正。

## 7. 第二個研究：叫牌（`bidding.ts`，`e5-t66`、`e5-t67`）

```bash
npm run sim -- bidding --deals 15000 --system gib --threads 8     # 2/1，約 25–50 分鐘（看電腦多忙）
npm run sim -- bidding --deals 20000 --system tku --threads 8     # 淡江制度
npm run sim -- compete --deals 10000 --system gib                 # 只看競叫的決策點（同一套方法）
npm run sim -- bidding --deals 15000 --system gib --analyse --practice shared/practice-sets  # 重做報告、寫出練習牌組
```

**方法**：固定牌組每一副由四個 TKB（`--system`）叫完；**每一個叫品**都是一個決策點，分成十一類：

| 群 | 類別 | 什麼時候 |
| --- | --- | --- |
| 建設性（對手只 Pass） | 開叫與否、第一次答叫、部分合約／邀請／成局（目前合約在成局以下）、成局或滿貫（已到成局） | |
| 對手先開叫（防禦叫牌） | 直接位置蓋叫／不叫、技術性賭倍（短在對手花色、其他三門 3 張以上、11 點以上）、平衡位置（再 Pass 就結束）、對抗阻擊、對抗 1NT、犧牲與處罰賭倍（我方叫過、對手在三線以上，或對手第一次叫到成局） | 對手的開叫本身、一線答叫或單加叫之後；對手 2♣／2NT 強開叫、問 A 的叫品與回答不算 |
| 我方開叫、對手插叫 | 我方開叫被干擾 | |

每個決策點拿 TKB 的叫品跟一兩個**替代叫品**比：Pass、同一門少叫或多叫一線、成局（有 8 張配合的高花、3NT、低花）、滿貫、賭倍、爭叫最長的 5 張花色、犧牲在我方的配合。替代叫品只用叫牌者看得到的（自己的牌、機器人自己讀出的同伴點力與張數，`TableReading`），例如「同伴最少點數＋自己 ≧ 21 才試成局」「可能的合計 ≧ 30 才試滿貫」；同伴迫叫之後不試 Pass，人工叫品（Stayman、RKCB、扣叫）不試替代。每個替代叫品都讓四個 TKB 從那裡叫完，最後的合約用那一副的 DD 表算分、換成 IMP；另外算 TKB 的結果對 **par**（DDS `DealerPar`）。par 是雙明手、兩邊都叫到最好，所以系統性偏向叫高（成局、滿貫、便宜的犧牲都算到），**真弱點＝兩個指標都差**：TKB 輸給替代叫品，而且那一類離 par 也遠。研究讀整副牌（離線分析，雙方實際點力與配合只用來分表），機器人叫牌仍然只看自己的牌。

**讀法**：

- **TKB − 替代**：每個對照 TKB 比替代叫品多贏的 IMP，正的是 TKB 對。
- **每千副**：那一格的總和 ÷ 副數 × 1,000——每一千副牌，總是改叫替代叫品會差（正）或好（負）幾個 IMP。**修規則照這個排先後**（頻率 × 平均損失），不是照平均損失。
- **細格**：再依雙方實際點力分（`–17` … `33+`），看門檻在哪裡不對；點力是雙方真的有的，機器人看不到，所以細格告訴我們「哪裡」，改規則時要換成叫牌者看得到的條件。
- 報告另外有每一類依點力的「少叫／多叫」表（TKB 對 Pass 或少叫一線、對多叫一線或出手），以及每類 TKB 損失最大的 15 個牌例。

替代叫品是「合理但簡單」的叫法，大部分時候不如 TKB 的規則，所以每一類的總平均幾乎都是正的；有用的是平均為負的格。

## 8. 一百萬副的結論與據此改的規則（`e6-t44`，2026-10-26）

社長的電腦把兩種制度各跑了 1,000,000 副（`leads-tku-eval-v1-tku-r1ab157e5`、`leads-tku-eval-v1-gib-r481397f0`，各約 99 萬副有合約）。平均損失：淡江無王 0.438、王牌 0.204 墩；2/1 無王 0.434、王牌 0.209 墩。標準誤 0.001–0.01 墩，隨機副已經夠，缺的是「攻哪一門」的細部條件和雙明手偏差。

### 方法：重播，不用再解 DDS

首攻紀錄存了**每一張**首攻的雙明手結果，而同一門攻哪一張由「01 第 4」固定（`lead-card.ts`，社團規則，不能改），所以只要知道新規則攻哪一門，就能直接在一百萬副上算出新舊首攻的差別：

- `npm run sim -- replay --out <紀錄檔>`（`replay.ts`）：從種子發牌、照紀錄的叫牌重叫、讓這份程式的 TKB（只用它的 `View`）首攻，跟紀錄裡的舊首攻比：實際牌局的墩數、倒合約、IMP（用得分差換算），以及「舊類型 → 新類型」的表。`--changed 檔` 把首攻改變的副號寫出來。
- 探索時用一個只看首攻者特徵（各門張數與大牌、叫牌讀出的同伴與莊家方花色、合約）的小程式重現舊規則（一百萬副 100% 一致），一次 17 秒試一組規則；挑出來的規則寫進 `play.ts` 後再用 `replay` 確認兩邊一樣。
- **單明手校正**：從「任何候選規則會改變首攻」的 167,077 副（淡江）均勻抽 8,000 副，用改規則**以前**的 TKB 跑 `leads --boards 清單 --samples 20`（每副 20 個首攻者自己的佈局，`sampled.biased` 另外記莊家扣 0.25、0.5 墩後的倒合約率與分數），再用 `replay` 比新舊。新首攻在抽樣下也要更好，而且三個偏差值都要是正的，才採用。

### 損失集中在哪裡

依「TKB 攻的那門」與「最佳的那門」的類型切開（每門用社團的慣例牌），首攻者看得到、又差最多的是：

1. **無王攻了莊家方叫過的花色**（叫牌讀出 4 張以上）：例如攻 Axxx、Kxxx、Jxxx 而那門是莊家方的，改攻沒叫過的三張小牌平均多 0.2–0.26 墩、0.6–1.0 IMP。連莊家方花色裡的連張也一樣（O:QJTx 對三張小牌 +0.16 墩）。
2. **王牌合約從單獨的 K（Q、J）底下攻出**：Kxxx(x) 對沒大牌的雙張 +0.10～+0.19 墩、對三張小牌 +0.07 墩、對 A 帶 5 張以上（攻 A）+0.09～+0.14 墩。
3. **同伴叫過、但正是王牌的花色**：淡江制度的 1♣／1♦ 可能很短、2/1 的扣叫，莊家卻打那門王；舊規則照樣攻同伴的花色＝攻王牌。高花 +0.3 墩、低花攻王牌對單張 +0.55 墩。
4. 小雙張：有王牌控制時比長門好（一百萬副 +0.055，§4 的觀念表），沒有控制時差不多（−0.013）。

### 改的規則（`shared/robot/play.ts` 的 `openingLead`，兩種制度共用）

| 規則 | 一百萬副（雙明手，實際牌局）：IMP／副、改變的副 | 單明手抽樣（改變的副，t = 0／0.25／0.5）：墩、倒合約 |
| --- | --- | --- |
| 1. 同伴的花色不是王牌才攻 | 淡江 +0.0042（1.24%），2/1 +0.0001（0.02%） | 568 副：+0.113 墩；+2.66／+2.61／+2.56 個百分點 |
| 2. 無王：莊家方叫過的花色排後面、也不攻那裡的連張 | 淡江無王 +0.068（17.2%），2/1 無王 +0.071（16.5%） | 2,535 副：+0.242 墩；+5.14／+5.30／+5.45 |
| 3. 王牌合約：同上（也不攻那裡的雙張） | 淡江 +0.0038，2/1 +0.0058（全部副） | 1,079 副：+0.077 墩；+1.28／+1.40／+1.53 |
| 4. 王牌合約：從單獨大牌底下攻出的花色排在沒大牌的後面 | 淡江 +0.0084，2/1 +0.0109 | 2,167 副：+0.063 墩；+1.53／+1.57／+1.60 |

規則寫進 `play.ts` 後用 `replay` 重播整個一百萬副，跟探索程式的數字一樣：淡江首攻改變 138,229 副（14.0%），+0.0139 ± 0.0003 墩、**+0.039 ± 0.001 IMP／副**；2/1 148,466 副（15.0%），+0.0156 ± 0.0003 墩、**+0.043 ± 0.001**。用新規則從頭跑的前 3,600 副，叫牌與每張首攻的 DD 跟舊紀錄逐副相同，所以重播等於重跑。

（一百萬副那欄是依序加上每一條的增量，IMP／副對全部副平均；抽樣那欄是每一條對前一條、只算首攻改變的副。）平均每副多 0.014 墩（淡江：無王 +0.023、高花 +0.008、低花 +0.014；倒合約 28.57% → 28.90%）、2/1 多 0.016 墩（無王 +0.026、高花 +0.009、低花 +0.012；25.49% → 25.85%）；雙明手下 TKB 首攻的平均損失淡江 0.277 → 0.263、2/1 0.286 → 0.270 墩。無王的規則 2 在單明手下（+0.24 墩）比雙明手（+0.12 墩）還好：雙明手的莊家打自己的長門不會失誤，所以低估了「不攻莊家的花色」。

## 9. 滿貫附近的叫牌樣本（`--deck slam`，V4d，2026-10-30）

隨機牌裡雙方合計 30 點以上的副不到一成，§7 的「成局或滿貫」一類只有幾百個對照。`--deck slam` 換成**滿貫區的牌組**：南北合計 30–36 點，或 26–29 點而且有 9 張配合（一家 5 張、一家 4 張以上）；符合條件的牌每一副機率一樣（`shared/dealer.ts` 的拒絕抽樣，`eval/deals.ts` 的 `SLAM_CONDITIONS`），種子是 `slam:<種子>`（例如 `slam:tku-eval-v1`，檔名裡寫成 `slam-tku-eval-v1`）。發牌者與身價照副號循環，所以四個座位都會開叫、四種身價都有。同一個選項也給 `npm run eval` 用：機器人自己打完，比雙明手更接近真的結果。

```bash
npm run sim -- bidding --deck slam --deals 5000 --system tku --threads 5   # 約 8 分鐘（5 執行緒，電腦跟別的模擬共用）
npm run sim -- bidding --deck slam --deals 5000 --system gib --threads 5
npm run eval -- --a tku --b tku@../main --deck slam --set 5000             # 這份程式對 main，滿貫區 5,000 副，約 2 分鐘
```

叫牌研究的報告多一張**滿貫區**的表（強方合計 26 點以上的副，隨機牌組也有）：強方（點力多的一方）任一家、任一王牌雙明手最多幾墩 × TKB 最後叫到哪裡（沒叫到滿貫、小滿貫、大滿貫；對方的合約算「沒叫到」），每格是副數與 TKB 對 par 的 IMP。紀錄多一個 `strong`（強方、點力、最多幾墩、TKB 的分數）；強方 26 點以上的副就算沒有決策點也會解 DD 表。

- 要更準的判斷，下一步是在這個牌組上跑 `compare`（單明手抽樣）看滿貫合約的坐莊，或用 `--dd-bias` 校正雙明手的偏差（§2）。
